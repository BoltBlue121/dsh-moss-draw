# 05 · 版本兼容矩阵

本插件只对下表列出的 DSH Desktop 版本声称「已验证」。矩阵外的版本一律视为未验证，除非按第 4 节完成复验并显式把版本写进声明。

本文用四个占位符：`<repo>` 表示仓库根目录，`<DshHome>` 表示 DSH home（默认 `%USERPROFILE%\.dsh`），`<workspaceRoot>` 表示允许插件读图的绝对目录，`<comfy-host>` 表示 ComfyUI 的主机名或地址。

## 1. 0.8.0 基线验证矩阵

0.9.0 保留这些版本声明。以下历史用例数属于 0.8.0；当前版本的复测结果以本次发布验收为准。

| DSH Desktop | 结论 | 验证证据 | 状态 |
|---|---|---|---|
| `0.2.1-rc.2` | 已验证 | 1008 个单元测试 + real-loader cold load + client bundle load | 可对外声称兼容 |
| `0.2.1-rc.3` | 已验证 | 1008 个单元测试 + real-loader cold load + client bundle load | 可对外声称兼容 |
| `0.2.1-rc.5` | 已验证 | 1008 个单元测试 + real-loader cold load + client bundle load | 可对外声称兼容 |
| 其它版本 | 未验证 | 无 | 不得声称兼容 |

「1008 个单元测试」是 `plugin/tests/*.test.mjs` 在官方 `app.asar` SDK 下的用例总数，取自验收日志 `unit-tests.log` 的汇总行；该数字会随仓库演进变化，引用时应连同证据文件一起给出，而不是只报数字。

已验证环境：Windows Desktop profile，node 24.21.0、pnpm 11.28.5、Electron 44.x，SDK 位于 `resources\app.asar\dsh\`。

### 声明在哪里

| 位置 | 内容 |
|---|---|
| `plugin/package.json` 的 `engines.dsh` | `0.2.1-rc.2 \|\| 0.2.1-rc.3 \|\| 0.2.1-rc.5` |
| `plugin/package.json` 的 `peerDependencies` | 每个 `@deepseek-ai/dsh-*` 都是同一组三版本范围 |
| `@deepseek-ai/schemastery` / `@deepseek-ai/cordis` | 精确 `3.18.5` / `4.0.5` |
| `install/probe.mjs` 的 `VERIFIED_DSH_VERSIONS` | `['0.2.1-rc.2', '0.2.1-rc.3', '0.2.1-rc.5']` |

三处必须同时包含某个版本，该版本才算声明在矩阵内；只改其中一处会造成「探测通过但 Host 解析不到 peer」或反之。

## 2. 「已验证」指什么

已验证 = 在指定 DSH Desktop 版本上，下列三层全部通过，且证据文件可查：

| 层 | 证据文件 | 通过条件 |
|---|---|---|
| 单元与集成测试 | `verification/unit-tests.log` | `fail` 为 0、`tests` 大于 0，退出码 0 |
| real-loader cold load | `verification/cold-load.json` | `pass: true`；`session.tools` 恰为 7 个 `art_*`；`guides` 按 9 页读取；`networkAttempts` 与 `serverAttempts` 为空 |
| client bundle load | `verification/client-load.json` | `pass: true`；注册 1 个页签、2 个槽位；`disposals` 正常；bundle 内无私有标记 |

一键收集：

```powershell
.\verify\run-verify.ps1 `
  -KitRoot . `
  -DesktopDir "$env:LOCALAPPDATA\Programs\DeepSeek Harness" `
  -DshHome "$env:USERPROFILE\.dsh" `
  -RequireVerifiedVersion
```

`-RequireVerifiedVersion` 让探测发现矩阵外版本时直接判失败；不加时只告警并继续，适合在准备拓宽矩阵时先看结果。

## 3. 「已验证」不指什么

- 不证明画质、审美、多人/多参考身份一致性、四参考、复杂遮挡或长时运行的缓存行为；这些都需要逐图人工验收。
- 不证明真实 GUI 渲染与交互手感；client bundle load 只证明模块能解析、按 `inject` 声明等待注入、注册页签与槽位并干净销毁。
- 不证明 GPU 出图链路在部署方 ComfyUI 上可用：模型、节点与显存由部署方负责，cold load / client load 都不提交推理。
- 不覆盖非 Windows 平台、Web profile、其它 Electron/Node 组合、或部署方自行修改过的包（改了 `src\`、`client\` 或模板就不再是同一份被测对象）。
- 不覆盖部署方自备的 LoRA 与画风实验。
- 升级 DSH 后旧证据立即失效：必须在新版本上重跑本文第 4 节，再决定是否加载。

## 4. 矩阵外版本与复验

### 4.1 矩阵外会发生什么

| 场景 | 行为 |
|---|---|
| `install/probe.mjs` 发现矩阵外版本，未豁免 | 退出码 `2`，`decision: "refused"`，并在 `warnings` 里给出矩阵说明 |
| `install/install.ps1` 探测返回 `2` | 脚本以退出码 `2` 中止，不写任何文件 |
| 显式 `--allow-unverified-version`（脚本里是 `-AllowUnverifiedVersion`） | 退出码 `0`，`decision: "unverified-override"`；安装继续 |
| `verify/run-verify.ps1` 未加 `-RequireVerifiedVersion` | 只告警，其它层照跑 |
| `verify/run-verify.ps1` 加 `-RequireVerifiedVersion` | 探测层判失败，总判定 `pass: false` |

豁免后的约束：该部署只能标注为 **experimental**，不得对外宣称兼容；要么完成第 4.2 节的复验并把版本写进三处声明，要么保持 experimental 并在部署记录里注明。

### 4.2 复验一个新 DSH 版本

顺序不能颠倒：先跑证据，再改声明。

1. **准备**：装好新的 DSH Desktop，确认 `resources\app.asar` 存在；退出其它 Host 实例。
2. **探测**：确认新版本号，并记录它当前的 `decision`（此时应为 `refused`）。

```powershell
$env:ELECTRON_RUN_AS_NODE = '1'
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\install\probe.mjs --desktop-dir "$env:LOCALAPPDATA\Programs\DeepSeek Harness" --json
```

3. **单元测试**：用新 SDK 跑 `plugin/tests/*.test.mjs`。SDK API 变化通常会在这里暴露为断言失败或 `MOSS_SDK_CAPABILITY`。

```powershell
$env:ELECTRON_RUN_AS_NODE = '1'
$env:MOSS_SDK_PACKAGE = "$env:LOCALAPPDATA\Programs\DeepSeek Harness\resources\app.asar\dsh\package.json"
Set-Location .\plugin
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" --test tests\*.test.mjs
Set-Location ..
```

4. **cold load**：官方真实 loader 必须能在假 profile 上加载本包并挂上 `ai-draw` 预设。

```powershell
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\verify\cold-load.cjs --kit . --work .\.verify-work --out .\verification\cold-load.json
```

5. **client load**：客户端 bundle 必须仍能注册页签与槽位、正常销毁。

```powershell
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\verify\client-load.cjs --kit . --work .\.verify-work --out .\verification\client-load.json
```

6. **发布面检查**：`sanitize-scan` 与 `package-integrity` 仍为 0 命中/一致。
7. **拓宽声明**（只有在 3–6 全绿后才做，且三处同步）：
   - `plugin/package.json` 的 `engines.dsh` 追加新版本；
   - 每个 `@deepseek-ai/dsh-*` 的 `peerDependencies` 范围追加新版本；
   - `install/probe.mjs` 的 `VERIFIED_DSH_VERSIONS` 追加新版本。
8. **回归**：用 `-RequireVerifiedVersion` 重跑 `run-verify.ps1`，确认探测层也通过。
9. **同步文档**：更新本文件的矩阵表、[01-适配清单.md](01-适配清单.md) 第 6 节、根 [README.md](../README.md) 的版本表与 `plugin/README.md` 的版本段，并附上新证据文件路径。

如果第 3–5 步有失败，说明该 DSH 版本需要代码适配（SDK 接口、注入点、客户端模块约定）。在适配完成并复验通过之前，不要把它写进声明，也不要发布称兼容。

### 4.3 降级与并存

- 回退 DSH 版本后，旧版本的证据不能直接复用：那台机器上的 `verification\` 已被新版本覆盖过，需重跑。
- 同一台机器上并存多个 DSH 版本时，`probe.mjs` 与验收脚本都只按 `-DesktopDir` 指向的那一份运行；证据要写明对应的 `DesktopDir` 与版本号。
- profile 侧本仓库不提供、也不要求任何版本豁免机制；不要用 `compatibility.json` 之类的旁路绕过本文的判定。
