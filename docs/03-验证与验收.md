# 03 · 验证与验收

本文说明仓库自带的分层验收：每一层跑什么、证明什么、**不**证明什么，证据文件怎么读，以及真实会话里必须人工完成的冒烟清单。

本文用四个占位符：`<repo>` 表示仓库根目录，`<DshHome>` 表示 DSH home（默认 `%USERPROFILE%\.dsh`），`<workspaceRoot>` 表示允许插件读图的绝对目录，`<comfy-host>` 表示 ComfyUI 的主机名或地址。

## 1. 分层与边界

验收共 5 层，外加 1 个前置探测。前置探测不是「层」，它只判断这台机器的 DSH 版本与 SDK 结构能否加载插件。

| 层 | 跑什么 | 证明什么 | 不证明什么 |
|---|---|---|---|
| 前置 | `install/probe.mjs` | DSH 版本在矩阵内、node 24、12 个 SDK 包可从 `app.asar` 解析、profile 注册状态 | 插件能否加载、能否出图 |
| 1 | `plugin/tests/*.test.mjs`（验收记录 1008 个用例，用例数随仓库演进） | 工具契约、参数校验、存储与账本、区域合成、工作台状态机在固定 SDK 下的行为 | 真实 Host 会话、真实模型行为、画质 |
| 2 | `verify/cold-load.cjs` | 官方真实 loader 从假 profile 发现并加载本包、挂载 `ai-draw` 预设、7 个 `art_*` 工具应答、指南与模板确实从包内读取、工作台 RPC 通路、客户端 bundle 被发现并可由 Host 提供、零网络 | 真实 profile 数据、GUI 渲染、GPU 出图 |
| 3 | `verify/client-load.cjs` | 随包客户端 bundle 能解析、遵守 `inject` 声明并等待注入、注册页签与槽位、可正常销毁、bundle 内不含私有画风/渠道标记、零网络 | 视觉布局、交互手感、真实浏览器/CSS |
| 4 | `verify/sanitize-scan.mjs` | 面向发布面的静态扫描 0 命中（个人路径、内网/隧道地址、渠道名、私有画风名、剧情/角色名、凭据、个人邮箱域） | 未被规则覆盖的个人信息；语义上的隐私问题 |
| 5 | `verify/verify-package.mjs` | tarball 的 sha256 与 `SHA256SUMS.txt`、`package-manifest.json` 一致；解包后的文件树逐文件字节与哈希一致；解包树再过一次 sanitize 扫描 | 安装后的运行行为 |

第 2、3 层需要官方 Desktop 二进制以 Node 模式运行（SDK 在 `resources\app.asar` 里，系统 node 读不到），但**不使用网络、不使用 GPU**。

## 2. 一键运行

```powershell
.\verify\run-verify.ps1 `
  -KitRoot . `
  -DesktopDir "$env:LOCALAPPDATA\Programs\DeepSeek Harness" `
  -DshHome "$env:USERPROFILE\.dsh"
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-KitRoot` | 脚本上一级目录（即 `<repo>`） | 含 `plugin\`、`install\`、`verify\`、`dist\` 的目录 |
| `-DesktopDir` | `%LOCALAPPDATA%\Programs\DeepSeek Harness` 或 `DSH_DESKTOP_DIR` | 官方 Desktop 目录 |
| `-DshHome` | 无 | 只用于探测时报告 profile 状态；不传也能跑 |
| `-Profile` | `desktop` | 同上，仅用于报告 |
| `-OutDir` | `<repo>\verification` | 证据与日志目录 |
| `-SkipPackage` | 关 | 跳过第 5 层（`dist\` 尚未构建时用） |
| `-RequireVerifiedVersion` | 关 | 探测发现矩阵外版本时判失败；默认只告警 |

脚本会按顺序执行：探测 → 单元测试 → cold load → client load → sanitize 扫描 → 包完整性，并把每一步的 `pass` 与摘要写进 `verify-summary.json`。它不重启 DSH、不提交 GPU 任务、不触碰真实 profile。

`-OutDir` 是运行产物；仓库根的 `.gitignore` 已忽略 `verification/`、`.verify-work/`、`.work/`，这些目录不会进提交。

第 5 层需要 `dist\*.tgz`：仓库里的 tarball 由 `node .\dist\build-package.mjs` 生成（同时产出 `package-manifest.json` 与 `SHA256SUMS.txt`）。没有构建过就先构建，或加 `-SkipPackage` 跳过该层并明确记录跳过原因。

## 3. 证据怎么读

`verification\` 下通常包含：

| 文件 | 内容 |
|---|---|
| `verify-summary.json` | 总判定：`pass`、`failedSteps`、逐层 `steps.<name>.pass` 与 `data` |
| `probe.json` / `probe.log` | DSH 版本、node、Electron、SDK 解析、profile 注册状态、`decision` |
| `unit-tests.log` | Node test reporter 输出；末尾汇总 `tests` / `pass` / `fail` / `skipped` |
| `cold-load.json` / `cold-load.log` | `pass`、`session.tools`（7 个工具名）、`guides`（指南页数）、`context.mossStyles`、`client.served`（客户端字节数与 sha256）、`networkAttempts` 与 `serverAttempts`（必须为空） |
| `client-load.json` / `client-load.log` | `pass`、`registrations.tab`（页签 id）、`injectGate`、`disposals`、`checks.noPrivateStrings` |
| `sanitize-scan.json` / `.log` | `scannedFiles`、`hitCount`、`hits[]`（`file`/`line`/`pattern`/`match`/`excerpt`） |
| `package-integrity.json` / `.log` | tarball 的 `bytes`/`sha256` 与 manifest 比对、解包树逐文件比对、`mismatches[]` |
| `sanitize-scan-tgz.json` | 解包后 `package/` 的再次扫描 |
| `tgz-extract/` | 第 5 层的解包树（证据目录，不入库） |

判定顺序建议：先看 `verify-summary.json` 的 `pass` 与 `failedSteps`，再按失败层打开对应 JSON；日志用来定位脚本异常，不要只看日志的末行。

两个读法上的注意点：

- `verify-summary.json` 的 `host.node` 记录的是 Desktop 可执行文件的 `FileVersion` 字符串（脚本实现如此），真实 node 版本以 `probe.json` 的 `host.node` 为准。
- `cold-load.json` 的 `pass` 只在全部断言通过时写 `true`；失败时文件里会有 `error.message` 与堆栈。`networkAttempts` 与 `serverAttempts` 非空即视为破坏「零网络」前提。

## 4. 单独跑某一层

> 下面的 `node` 指任意 node 24。新机器上若没有 `node` 在 PATH 里，用官方 Desktop 的 Node 模式代替：先设 `$env:ELECTRON_RUN_AS_NODE = '1'`，再执行 `& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" <脚本> <参数>`。

```powershell
# 前置探测
$env:ELECTRON_RUN_AS_NODE = '1'
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\install\probe.mjs --desktop-dir "$env:LOCALAPPDATA\Programs\DeepSeek Harness" --json

# 第 1 层：单元测试（需要 MOSS_SDK_PACKAGE 指向 app.asar 内的 DSH 包）
$env:ELECTRON_RUN_AS_NODE = '1'
$env:MOSS_SDK_PACKAGE = "$env:LOCALAPPDATA\Programs\DeepSeek Harness\resources\app.asar\dsh\package.json"
Set-Location .\plugin
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" --test tests\*.test.mjs
Set-Location ..

# 第 2 层：cold load（会写 .verify-work\ 的 boot-graph.json 与 discovered-client.js）
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\verify\cold-load.cjs --kit . --work .\.verify-work --out .\verification\cold-load.json

# 第 3 层：client load（复用上一层的产物）
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
  .\verify\client-load.cjs --kit . --work .\.verify-work --out .\verification\client-load.json

# 第 4 层：发布面扫描，0 命中才 exit 0
node .\verify\sanitize-scan.mjs --dir .\plugin --out .\verification\sanitize-scan.json

# 第 5 层：tarball 与 manifest/校验和比对
node .\verify\verify-package.mjs --kit . --tgz .\dist\dsh-external-dsh-moss-draw-0.9.0.tgz --out .\verification\package-integrity.json
```

`MOSS_SDK_PACKAGE` 必须指向 `app.asar` 内的 `dsh\package.json`；指向系统 node 的 SDK 会得到 `MOSS_SDK_CAPABILITY` 或解析失败。第 3 层依赖第 2 层的 `.verify-work\boot-graph.json` 与 `.verify-work\discovered-client.js`，顺序不能颠倒。

## 5. 指南 topic 清点

`art_guide` 服务 9 个 topic，单次最多 9000 字符，`next_offset` 为 null 表示读完：

| topic | 用途 |
|---|---|
| `quick` | 工具契约与执行纪律入口，首步读它 |
| `index` | 索引：各页用途与读取建议 |
| `moss-modes` | MOSS 参数、模式与验证边界（含 `style=none`、无内置 LoRA 口径） |
| `k2` | K2（Krea2）t2i 参数与限制 |
| `qwen` | Qwen-Image-2.1 edit 契约 |
| `regions` | 底图划区、绑定角色参考、预览后授权执行 |
| `workbench` | 工作台文档、提案/采纳、revision 冲突、3D 体块投影 |
| `studio` | 工作台能力地图、执行顺序、同一页续画、错误分流 |
| `promptcraft` | 提示词手艺：构图、复刻、失败对策、审图十项 |

`art_guide` 只读本插件自带的页面，不附带第三方提示词库原文。

## 6. 真实会话冒烟清单

安装完成后在真实会话里逐项确认；下列各项都不需要 GPU：

- [ ] 正常重启 DSH 后，Agent preset 出现「AI 画画」（id `ai-draw`）。
- [ ] 新建空白会话能选中该预设；右侧栏出现「AI画画工作台」页签，对话区出现「MOSS工作台」视图。
- [ ] 原生模型栏选中一个能看图的模型渠道，模型能稳定调用工具（不靠猜字段）。
- [ ] `art_guide quick` 返回正文；再依次读 `index` 与其余 7 个参考页 topic 都能返回，长页能用 `next_offset` 续读。
- [ ] 工具清单恰好是 7 个：`art_guide`、`art_context`、`art_generate`、`art_run`、`art_review`、`art_view`、`art_deliver`；没有继承来的其它工具。
- [ ] 工作台可新建系列与页、改标题/caption 后 `revision` 递增；`art_context({document_id})` 能读回同一文档。
- [ ] `art_generate({backend:'moss',mode:'regions',action:'draft',...})` 只产出计划与预览（draft 不提交推理），`art_view` 能看 `preview`。
- [ ] 参数校验可离线验证：`backend:'qwen'` 带 `loras`、`style` 非 `none`、`loras` 超过 4 条或文件名重复，都应在本地被拒绝。

以下每一项都需要部署方**显式决定**后才做，属于真实 GPU 出图：

- [ ] 授权一次 t2i：给稳定 `request_id`，`art_run` 等待，`art_view` 看结果，`art_review` 记录观察与下一改动，`art_deliver` 交付。
- [ ] 授权一次 edit 或 regions 执行，并逐图检查区域外像素、遮挡与身份一致性。
- [ ] 若要用多 LoRA，先在 ComfyUI 的 `loras/` 放好文件，再用 `loras:[{file,strength,trigger}]` 验证顺序与触发词。

边界：**GPU 任务是否提交始终是部署方的显式决定**。`verify/` 下的脚本只用假 profile、内存内传输与本地进程，从不向 ComfyUI 提交任何任务；真实会话里的第一次出图也不属于安装或验收脚本的一部分。

## 7. 通过标准与失败处理

一次可以对外引用的验收，至少满足：

1. `verify-summary.json` 的 `pass` 为 `true`，`failedSteps` 为空。
2. `probe.json` 的 `decision` 为 `supported`，`checks.sdkResolved` 为 `true`。
3. `unit-tests.log` 的 `fail` 为 0 且 `tests` 大于 0。
4. `cold-load.json` 与 `client-load.json` 的 `pass` 为 `true`，且 `networkAttempts`/`serverAttempts` 为空。
5. `sanitize-scan.json` 的 `hitCount` 为 0（含解包后的 `sanitize-scan-tgz.json`）。
6. `package-integrity.json` 的 `pass` 为 `true`（未跳过第 5 层时）。

失败时的处理：

| 失败层 | 先查 |
|---|---|
| probe | `-DesktopDir` 是否指对；是否用 Desktop 二进制而非系统 node；`app.asar` 是否存在 |
| unit-tests | `MOSS_SDK_PACKAGE` 是否指向 `app.asar` 内 `dsh\package.json`；工作目录是否为 `plugin\` |
| cold-load | `.verify-work` 是否被旧产物污染（可整目录删除后重跑）；是否有磁盘权限问题 |
| client-load | 是否先跑过 cold-load；`client\lib\client.js` 是否被手工改过 |
| sanitize-scan | 按 `hits[].file` 与 `pattern` 修源文件，不要改扫描器或把真实值藏进注释 |
| package-integrity | 先 `node .\dist\build-package.mjs` 重建，再核对 `SHA256SUMS.txt` |

## 8. 不在验收范围

- 画质、审美、多人/多参考身份一致性、四参考、复杂遮挡、长时运行的缓存行为：都需要逐图人工判断。
- 真实浏览器里的视觉布局与交互手感：client load 只证明模块能加载、注册与销毁。
- 非 Windows 平台、Web profile、其它 Electron/Node 组合。
- 部署方自备的模型、节点与 LoRA 的质量与许可证。
- 升级 DSH 之后的兼容性：旧证据在升级后失效，必须重跑本文全部层级，见 [05-版本兼容矩阵.md](05-版本兼容矩阵.md)。
